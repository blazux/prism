# Private presentation demos

This recipe runs independent personal and shared Prism installations behind an
existing HTTPS reverse proxy. Each installation has its own database, workspace,
notes, encryption key and Docker service daemon. Only the owner uses these demos.

## Files and configuration

The deployed files live in `/opt/prism-demos` on the VPS. Each Compose project
uses the same `compose.yaml` and its own private `.env.mono` or `.env.multi` file.
The projects are `prism-demo-mono` and `prism-demo-multi`. Their web servers bind
to loopback ports 4881 and 4882; HAProxy serves the two HTTPS hostnames.

Configure these values in each environment file:

- `DEMO_NAME`, `DEMO_PORT` and `MULTI_USER` for the installation.
- `PRISM_IMAGE` and `WORKSPACE_IMAGE` for the tested release artifacts.
- `POSTGRES_IMAGE` and `SEARXNG_IMAGE` using the pulled image digests.
- Independent random `PRISM_TOKEN`, `POSTGRES_PASSWORD` and `SEARXNG_SECRET`.
- `OPENAI_BASE_URL`, `CHAT_MODEL`, `EMBED_BACKEND` and `EMBED_MODEL` for an
  existing inference endpoint. Use Settings or the Admin console to configure
  an independent embedding connection when needed.

Protect environment files and the deployment directory with owner-only access.
The mounted `searxng.yml` contains no credential and must be readable inside its
container; `SEARXNG_SECRET` supplies its secret at runtime.

Build the CPU workspace using the commands in
[workspace/README.md](workspace/README.md). It includes Docker and Compose for
services created by the agent. Its Unix socket and Docker storage stay inside
that installation's workspace; its service ports are reached through Prism's
authenticated `/proxy/<port>/` routes.

The server retains an operator connection to the VPS Docker daemon for workspace
execution. The workspace is privileged for its inner daemon. This deployment is
intended for the owner's presentations, with authenticated access; it does not
provide isolation for untrusted public tenants.

## Initial start

Start one installation at a time:

```sh
cd /opt/prism-demos
docker compose -p prism-demo-mono --env-file .env.mono -f compose.yaml config --quiet
docker compose -p prism-demo-mono --env-file .env.mono -f compose.yaml up -d --no-build --pull never
docker compose -p prism-demo-multi --env-file .env.multi -f compose.yaml config --quiet
docker compose -p prism-demo-multi --env-file .env.multi -f compose.yaml up -d --no-build --pull never
```

Before enabling the public proxy routes, create the first multi-user account
through its loopback API and verify that it is the approved global administrator.
Create the presentation group and add the owner as its administrator. Configure
and test chat and embeddings in both installations. Keep demo data separate from
personal Prism volumes and integrations.

HAProxy must preserve `Host`, overwrite `X-Forwarded-Proto` with `https`, and allow
WebSocket connections. Use a long backend timeout for agent operations and a
tunnel timeout for the chat. Serve authenticated APIs only; keep ports 4881 and
4882 bound to loopback. The demo backends send `X-Robots-Tag: noindex, nofollow,
noarchive`.

Public account registration is disabled at the HTTPS proxy for both demo
hostnames. `/signup`, `/api/signup` and their trailing-slash variants return
403. Existing accounts can still sign in, and administration remains available
after authentication. Initial account creation uses the loopback API described
above.

Apply these rules to each demo backend, with port 4881 for mono and 4882 for
multi:

```haproxy
    http-request return status 403 content-type text/plain string "Registration is disabled for this private demo. Use your existing account." if { path,url_dec -m reg ^/(api/)?signup/?$ }
    http-after-response set-header Strict-Transport-Security "max-age=31536000"
    http-after-response set-header X-Robots-Tag "noindex, nofollow, noarchive"
    http-after-response set-header X-Content-Type-Options "nosniff"
    http-after-response set-header X-Frame-Options "SAMEORIGIN"
    http-after-response set-header Referrer-Policy "strict-origin-when-cross-origin"
    http-after-response set-header Permissions-Policy "camera=(self), microphone=(self), geolocation=(self)"
    http-after-response set-header Content-Security-Policy "frame-ancestors 'self'; base-uri 'self'; form-action 'self'"
```

These headers also cover responses generated by the proxy, including the
registration refusal. Same-origin framing keeps Prism's embedded applications
and widgets usable. This CSP does not restrict script or connection sources;
Prism's generated interfaces and connected services retain their existing
behavior. Browser permission prompts still apply to same-origin camera,
microphone and location requests.

The demo certificate is separate from the website certificate. The
`deploy-certificate.sh` hook checks the key and certificate, installs the PEM and
validates HAProxy before reloading it. The supplied systemd timer renews only the
`prism-demo` certificate through the existing Certbot DNS configuration.

## Update and verify

Wait for active agent work to finish. Change `PRISM_IMAGE` to the tested image,
then recreate only the server in each project:

```sh
docker compose -p prism-demo-mono --env-file .env.mono -f compose.yaml up -d --no-deps --no-build --pull never prism-server
docker compose -p prism-demo-multi --env-file .env.multi -f compose.yaml up -d --no-deps --no-build --pull never prism-server
```

Check HTTPS, sign-in, secure session cookies, a real agent tool call, workspace
file persistence and a service reached through `/proxy/<port>/`. Starting a
service with the same name in both demos must preserve both services. Check that
the website still responds and that anonymous requests to private APIs fail.
Do not remove volumes when updating; retain the previous image for rollback.

## Private connection to the models

Both demos use `http://10.203.54.2:4000/v1` through the `wg-prism` WireGuard
interface. The VPS peer is `10.203.54.1`; the GX10 peer is `10.203.54.2`. The GX10
initiates the encrypted transport to the VPS on UDP 51820. Each peer has one
`/32` route. Conversations and embeddings use this private endpoint.

Set `OPENAI_BASE_URL` in both environment files and update the saved **AI
provider** source: Settings in mono-user mode, Admin in multi-user mode. A saved
source takes precedence over the environment. Keep the source's model settings
and the existing embedding model. Changing the endpoint URL requires confirming
the document-index rebuild in Prism; the API retains the documents and original
index if rebuilding fails.

On both machines, `/etc/wireguard/wg-prism.conf` is root-only (`0600`). The
`prism-model-guard` service loads its dedicated nftables table before
`wg-quick@wg-prism`. Its rules allow only model traffic, block new reverse
connections and prevent the private destination from using another interface.
The GX10 guard checks Docker's original destination and port before DNAT.
Ports such as SSH and the inference engine's direct port are excluded.

On the VPS, `docker-model-network.conf` is installed as
`/etc/systemd/system/docker.service.d/30-model-network.conf`. Docker starts after
local VPN activation. WireGuard activation does not wait for the remote peer.
The GX10 and the models must be available for a presentation's AI features.

## Host firewall and maintenance

The deployed VPS uses `vps-firewall.service`, with the adjacent `vps-firewall`
loader installed in `/usr/local/sbin` and `vps-firewall.nft` installed in
`/etc/nftables.d`. The rules use the VPS interface `ens3`; review interface names
and required ports before applying this file on another host.

The input policy permits loopback, established traffic, ICMP/IPv6 neighbour and
MTU discovery, DHCP, TCP 22/80/443 and WireGuard UDP 51820. Other inbound traffic
is dropped. Output and forwarding rules also block the old public plaintext
model endpoint and prevent a private-model route from falling back to the WAN.
The loader replaces only its own table in one transaction, preserving Docker's
tables. Validate with `vps-firewall --check` and apply subsequent edits with
`systemctl reload vps-firewall`. Keep an automatic rollback timer until a new
SSH connection and external HTTPS checks pass. Avoid loading a global
`flush ruleset` while Docker is running.

Docker has `live-restore` enabled. Before a patch upgrade, wait for agent work
to finish and record container IDs and start times. Afterward, verify those
values, both inner Docker daemons, Bridge and the public sites. Local rollback
copies are stored under `/root/prism-security-backups`; off-host backups need
their own storage and retention policy.

## Proton Mail Bridge on the personal demo

Only `.env.mono` enables `COMPOSE_PROFILES=protonmail` and sets `PROTONMAIL_IMAGE`.
The Bridge joins the personal demo's private Docker network and keeps its own
`protonmail` volume. Its IMAP and SMTP ports are not published on the VPS.

To connect a Proton account, open the Bridge's interactive shell on the VPS:

```sh
/opt/prism-demos/proton-login.sh
```

Run `login`, complete account authentication, then use `info` to read the
Bridge-generated credentials. Run `exit` when finished; the script restarts the
Bridge service automatically.

In personal Prism, choose **Settings → Email → ProtonMail**. Use the credentials
printed by Bridge, IMAP `protonmail-bridge:143`, SMTP `protonmail-bridge:25`,
STARTTLS and the self-signed certificate option. The Proton account password is
used only in Bridge's login flow. See the
[Proton Mail help](../../docs/help/protonmail-bridge.md) for account requirements.
