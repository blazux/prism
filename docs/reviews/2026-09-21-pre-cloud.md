# Inventaire de Prism avant le chantier Cloud

Revue du 21 septembre 2026, base `ae12366` sur `main`. Aucun correctif applicatif ni déploiement dans cette passe.

## Conclusion

La couverture fonctionnelle est suffisante pour arrêter d'ajouter des applications et préparer le Cloud. L'architecture respecte globalement le principe de primitives composables : outils, code, fichiers, widgets, MCP, éditeurs et documentation embarquée.

En revanche, le code actuel ne constitue pas une frontière de sécurité pour des utilisateurs publics non fiables. Plusieurs défauts concernent aussi le mono-user exposé sur un réseau ou les déploiements partagés existants. Ils doivent être corrigés avant de prendre cette version comme base de la bêta.

Il n'est pas nécessaire de créer une deuxième implémentation de Prism. Il faut garder le produit commun et rendre explicites les frontières d'identité, d'exécution et de stockage. PrismCloud reste le provisionnement, les comptes publics, les invitations, l'administration et le support. Les groupes du mode entreprise ne deviennent pas des comptes Cloud.

## Méthode et limites

- Lecture des chemins principaux : configuration IA, auth, fichiers, secrets, outils, prompts, applications personnelles, widgets, crons, MCP, proxys, stockage, tests et publication Docker.
- `go test ./...`, `go vet ./...`, puis `go test -race ./... -count=1` avec PostgreSQL/pgvector jetable et les variables des tests d'intégration : réussite.
- Les 10 fichiers de tests JavaScript passent.
- Sondes temporaires avec fichiers, clés et jetons factices : résultats décrits ci-dessous. Aucun fichier secret réel lu, aucune charge Docker hostile lancée, aucune exploitation effectuée sur l'instance.
- Les tests nécessitant des comptes réels, un serveur CalDAV dédié ou des services externes non fournis restent sautés. Cette revue n'est pas une validation visuelle de toutes les pages, un audit de dépendances CVE, une mesure de charge ou un test de restauration complet.
- Les essais gVisor du dossier Prism Cloud ont été consultés comme résultats précédemment consignés ; ils n'ont pas été rejoués ici.

## Défauts à corriger dans Prism

Priorité 1 : sécurité ou frontière d'autorisation. Priorité 2 : exactitude, robustesse ou exploitation. « Reproduit » signifie une sonde locale non destructive ; « constat de code » précise une limite sans prétendre à une exploitation de bout en bout.

### R1 — Des fichiers générés sont accessibles sans authentification en mono-user — P1

`internal/server/auth_singleuser.go:33` ne refuse les requêtes anonymes que sur `/api/*` et `/ws`. Les routes `/data/`, `/screenshots/`, `/plugins/` sont servies par `internal/server/server.go:194`. La protection par PRISM_TOKEN ne couvre donc pas ces contenus. Le proxy des services est également hors du refus API.

**Reproduit :** avec AuthToken non vide et le même montage de FileServer, GET `/data/fixture.txt` sans cookie ni Bearer renvoie le contenu factice et HTTP 200.

**Impact :** des documents, résultats de scripts ou captures peuvent être lus par une personne ayant accès au serveur. En multi-user, les fichiers statiques partagés n'ont pas non plus de contrôle de propriétaire à leur lecture ; le middleware exige une connexion mais cela ne constitue pas une isolation par compte.

**Correction minimale :** distinguer les assets publics de l'application des contenus utilisateur, protéger ces derniers et vérifier leur propriétaire. Conserver les helpers et chemins simples vus par l'agent.

### R2 — Le retour OAuth peut injecter du HTML exécutable — P1

`internal/server/handlers_oauth.go:123` répercute le paramètre `error`, avant validation du state. `oauthDonePage`, ligne 157, concatène ensuite le message dans le HTML sans échappement. Le callback est public.

**Reproduit :** une chaîne de test contenant un élément script ressort telle quelle dans le corps HTML. Aucun navigateur n'a exécuté cette charge pendant la revue.

**Impact :** XSS réfléchi sur l'origine Prism, pouvant agir avec la session du navigateur qui ouvre un lien malveillant. HttpOnly ne bloque pas les requêtes authentifiées émises par un script de la même origine.

**Correction minimale :** template HTML avec échappement, messages contrôlés, validation du state et tests de régression.

### R3 — Les secrets OAuth Google/Microsoft ne sont pas classés comme secrets d'intégration — P1

`internal/oauthx/oauthx.go` stocke `oauth_<provider>_token` et `oauth_<provider>_client_secret`. `internal/memory/script_secrets.go:27` n'inclut pas ces noms dans les secrets réservés. `internal/agent/tools_misc.go:105` utilise ce classement pour filtrer l'environnement des scripts.

**Reproduit :** `oauth_google_token` et `oauth_microsoft_client_secret`, avec valeurs factices, traversent le filtre et sont injectables dans les scripts. Ils ne bénéficient pas non plus du blocage des noms réservés dans les routes génériques de secrets.

**Correction minimale :** centraliser la classification de tous les secrets d'intégration, couvrir les noms OAuth et tester stockage, lecture, suppression, liste et injection. Ne pas complexifier les paramètres des outils.

### R4 — Les outils fichiers n'appliquent pas une frontière de filesystem cohérente — P1

`internal/agent/tools_files.go:107` et `:130` contrôlent lexicalement le chemin mais suivent les liens symboliques. La clé de chiffrement est créée dans le volume workspace (`internal/server/server.go:129`). Le blocage du nom `.secret_key` dans `safeWorkspacePath` ne protège pas les outils agent ; un alias symbolique interne passe aussi ce contrôle de l'éditeur.

**Reproduit :** `read_file` lit un fichier factice hors workspace via un symlink ; il lit un fichier factice nommé `.secret_key` ; le validateur d'éditeur accepte un alias vers ce dernier.

**Impact :** les accès fichiers effectués côté serveur ne sont pas confinés au workspace réel. Le partage du volume contenant la clé avec le code exécuté compromet la séparation des secrets en environnement hostile.

**Correction minimale :** un accès fichiers commun et borné côté serveur, protection après résolution et séparation de la clé hors du volume d'exécution, avec migration compatible. Ne pas prétendre qu'un filtrage de noms sécurise un shell libre dans le même volume.

### R5 — Le validateur Docker Compose laisse passer des formes dangereuses — P1

`internal/agent/tools_docker_safety.go:44` ne contrôle qu'un sous-ensemble du YAML. `isHostPath` ne reconnaît que `/` et `~`. Les volumes de premier niveau, les inclusions et l'expansion effective de Compose ne sont pas couverts ; les erreurs de lecture/parsing ne bloquent pas ce validateur.

**Reproduit sans exécution Docker :** le contrôle accepte une source relative remontant hors projet, un volume nommé avec des options de bind hôte et un fichier ne contenant qu'une inclusion. Le serveur transmet ensuite le fichier au daemon avec son autorité (`internal/docker/manager.go:387`).

**Correction locale :** contrôler la configuration effective, fermer les cas non pris en charge et borner les projets administrables. **Cloud :** appliquer la décision déjà prise de ne donner aucune création de conteneur à l'utilisateur ou à l'agent. Un validateur Compose n'est pas la sandbox Cloud.

### R6 — Les jetons internes des agents de groupe deviennent administrateur global — P1

`internal/server/captoken.go:60` déduit l'identité du préfixe utilisateur du nom de session. Une session `room-g12` produit uid 0 ; `userForCapToken`, ligne 132, rend alors `serviceUser` administrateur global.

**Reproduit :** génération, vérification et résolution d'un jeton factice de groupe aboutissent à l'identité service. Les appels HTTP internes avec ce jeton n'ont donc pas les seules permissions du groupe.

**Correction minimale :** identité explicite pour les appels d'agents partagés, droits réellement limités au propriétaire/groupe et validation du contexte demandé. La variable `$PRISM_TOKEN` et les helpers peuvent rester inchangés pour l'agent. Le Cloud n'utilisera pas les groupes, mais ce défaut du mode partagé actuel doit être corrigé.

### R7 — Le callback OAuth perd le propriétaire qui a lancé la connexion — P1 fonctionnel / isolation

Le state stocké (`internal/server/handlers_oauth.go:19`, `:75`) ne contient aucun utilisateur. Le middleware autorise directement le callback public sans résoudre la session (`internal/server/auth.go`). L'échange utilise `s.userStore(r)` à la ligne 138, qui revient au store global sans utilisateur.

**Vérifié par code et sonde du middleware :** le callback arrive sans identité utilisateur. L'échange contre Google/Microsoft n'a pas été exécuté.

**Conséquence attendue :** les identifiants OAuth configurés par utilisateur ne sont pas relus dans le bon scope ; s'il existe une configuration globale utilisable, le jeton peut être enregistré globalement au lieu de l'utilisateur.

**Correction minimale :** lier state et propriétaire, consommer atomiquement ce contexte et vérifier le compte au retour. Pour plusieurs répliques, ce contexte doit être partagé et expirer durablement.

### R8 — Des échecs d'outils sont annoncés comme résultats réussis au framework — P2

`internal/agent/tools_docker.go`, `tools_files.go:91` et `tools_web.go:99` renvoient parfois un texte `ERROR...` ou `HTTP 500...` avec une erreur Go nulle. `internal/agent/executor.go:643` détermine succès/échec uniquement avec cette erreur. Le helper widget ne lève une exception que si la réponse porte `error` (`web/prism-widget.js`).

**Reproduit :** un faux serveur renvoyant HTTP 500 produit un résultat de `Execute` sans erreur. La qualification « completed » et l'absence de rejet côté helper résultent du contrat lu dans le code.

**Impact :** Activity et les widgets peuvent considérer un échec comme un succès ; l'agent doit interpréter du texte au lieu de recevoir un signal fiable.

**Correction minimale :** normaliser le résultat d'exécution à une seule frontière ; distinguer erreur de transport/exécution et réponse HTTP inspectée volontairement. Préserver le détail utile pour récupérer, sans convertir automatiquement toute réponse HTTP d'erreur en perte du résultat.

### R9 — Les éditions de crontab ne sont pas sérialisées — P2

Le serveur et l'agent ont deux implémentations de lecture/modification/installation. Le serveur emploie un fichier temporaire unique (`internal/server/handlers_cron.go:68`), l'agent un chemin commun `.crontab.tmp` (`internal/agent/tools_cron.go:519`). Aucun verrou commun ne couvre lecture + modification + installation + persistance.

**Constat de code :** deux éditions partant du même état peuvent perdre une modification ; le chemin temporaire commun ajoute une collision côté agent. Le remplacement par renommage protège une écriture, pas toute la transaction. Pas de reproduction concurrente sur un vrai cron dans cette revue.

**Correction minimale :** une primitive commune de mutation transactionnelle de la crontab, avec verrou partagé. Aucun paramètre supplémentaire à demander à l'agent.

### R10 — La publication ne rend pas les tests obligatoires et le build local n'exclut pas les secrets — P2

Le workflow `.github/workflows/docker.yml` construit et pousse les images sans étape Go/JS/tests d'intégration. Aucun `.dockerignore` n'est présent et le Dockerfile fait `COPY . .` dans le builder.

**Constat de code :** un build depuis un checkout local contenant `.env` peut transmettre ces fichiers au contexte et au cache de construction. Cela ne démontre pas leur présence dans l'image finale, qui copie seulement le binaire.

**Correction minimale :** tests bloquants avant publication, `.dockerignore` et politique explicite pour les secrets de build. Garder des tests de montée de version et de restauration avec données factices.

## Prompt, schémas et messages pour l'agent

### À conserver

- `prism_help` donne la documentation embarquée et la situation réelle de l'utilisateur ; les mêmes pages restent lisibles sans embeddings.
- Les primitives sont composables, et les helpers widgets cachent les détails de session, JSON et routage.
- Les mises à jour partielles, noms opaques renvoyés par les outils, pagination des longs mails et erreurs donnant les vrais noms évitent du travail au modèle.
- Les profils guidé/lean partagent leur texte source ; les aliases conservés passent par les noms canoniques pour les permissions.

### À améliorer sans créer une nouvelle collection d'outils

1. **Adapter le prompt aux capacités réelles.** Le rôle annonce un workspace Docker complet et le cœur enseigne Docker Compose et les URLs `.localhost`. Le Cloud ne doit pas recevoir ces passages quand les capacités ne sont pas disponibles. Les procédures qui restent identiques doivent rester identiques.
2. **Préciser la frontière des contenus externes.** Je n'ai pas trouvé de règle explicite couvrant mails, pages web, RAG et sorties MCP comme données non fiables qui ne donnent pas de nouvelles autorisations. Ajouter une règle courte ; les permissions doivent néanmoins être imposées par le serveur, même si le modèle ignore entièrement le prompt.
3. **Alléger ce qui coûte du contexte sans aider à chaque tour.** Mesure des seuls core+tail : 25 803 octets en guidé, 19 791 en lean ; catalogue statique de 45 outils : 49 144 octets de JSON, avant filtrage et contexte dynamique. Ce n'est pas une mesure de tokens ni du prompt final. Les tutoriels détaillés peuvent vivre dans `prism_help`/skills ; garder les contrats utiles dans les schémas. `agent_settings` est devenu dense avec les actions de sources et embeddings : améliorer son aide avant d'ajouter des outils.
4. **Supprimer les diagnostics trop certains.** `httpRequestError` attribue un timeout au site et exclut le réseau local sans preuve. Décrire le symptôme et la prochaine vérification au lieu d'inventer la cause.
5. **Synchroniser les recettes réseau.** Le prompt recommande un réseau externe `prism-net`, alors que Compose utilise normalement son réseau de projet et que `docker_run` découvre celui du workspace. Une recette doit obtenir la valeur réelle ou laisser Prism résoudre cela.
6. **Unifier les erreurs et statuts**, selon R8, puis mesurer les échecs réels. Un résultat « configuration sauvegardée » doit rester distinct de « configuration appliquée » ou « en cours ».

## Sécurité et secrets : acquis et limites

Acquis vérifiés dans le code : AES-256-GCM avec nonce aléatoire, publication prudente de la clé, valeurs de configuration IA non renvoyées au navigateur, collisions de noms de secrets contrôlées transactionnellement, mots de passe bcrypt, cookies HttpOnly/SameSite, vérifications de scopes applicatifs, retrait des credentials Prism des requêtes proxy, mail HTML dans une iframe sans scripts ni même origine, DOMPurify sur le Markdown du chat.

Ces acquis ne neutralisent pas R1 à R7. Les secrets de scripts sont volontairement accessibles au code qui les utilise ; il faut limiter cette capacité au propriétaire et au bon runtime. Les valeurs imprimées par un script peuvent revenir dans une conversation : le chiffrement au repos n'est pas un masque de sortie. Les comptes SQL, volumes, clé maître et socket Docker de la plateforme doivent rester hors de ce runtime.

Avant exposition publique : politique d'origine HTTP/WebSocket (CheckOrigin accepte tout actuellement), cookies Secure sur HTTPS, limitations de tentatives login/signup et de taille/durée des requêtes, bootstrap admin explicite. Le couple CountUsers/CreateUser du premier compte n'est pas une élection atomique. Le fallback multi-user sans store doit refuser l'accès plutôt que revenir à un mode potentiellement non authentifié. Ce sont des constats de code ; aucune attaque réseau ni course de création de comptes n'a été exécutée.

## Écarts Cloud déjà planifiés, toujours à implémenter

Les documents du dossier Prism Cloud prévoient déjà les bons sujets. La décision `docs/08-isolation-decision.md` retient gVisor comme candidat pour les workspaces, Compose pour la plateforme bêta, et aucune création Docker par le testeur. Il n'y a pas lieu de recommencer le choix d'orchestrateur dans cette revue.

1. **Propriétaire explicite partout** : IA/BYOK, secrets, fichiers, uploads, notes, outils personnalisés, skills, MCP, widgets, historique, RAG et canaux. Supprimer les retours implicites au scope global dans le profil Cloud.
2. **Exécution isolée** : workspace borné par utilisateur, volumes personnels, quotas CPU/RAM/PIDs/disque, plateforme et voisins inaccessibles, sorties réseau contrôlées. Les capacités web/code doivent rester utiles sans atteindre l'administration ou les credentials de la plateforme.
3. **Coordination** : sessions/tours/événements, state OAuth, éditeurs et approbations, règles email, canaux et migrations RAG. Les mutex et maps actuels ne couvrent qu'un processus ; doubler les serveurs peut doubler des tâches.
4. **Comptes et support** : invitations consommées une seule fois, suspension/révocation/récupération/suppression et MCP de support avec extraits choisis par le testeur. Ne pas reprendre tel quel le signup entreprise ni donner l'accès aux conversations à l'opérateur.
5. **Exploitation** : limites mesurées, sauvegarde coordonnée DB + fichiers + clé, restauration testée, health/readiness et métriques, versions épinglées et retour arrière explicite. La redondance applicative sur un VPS ne supprime pas sa panne unique.

## Ordre de travail proposé

1. Corriger R1–R7 dans le produit commun avec régressions de sécurité, sans déployer Cloud.
2. Corriger R8–R10 et rendre l'audit des opérations fiable ; revalider les parcours UI/outils concernés.
3. Introduire le contexte de propriétaire et l'adaptateur d'exécution Cloud derrière les mêmes primitives. Préserver mono-user local et multi-user entreprise par leurs profils explicites.
4. Implémenter les contrats Cloud existants, puis exécuter une matrice à deux utilisateurs et deux répliques : fichiers, secrets, MCP, outils, crons, arrêt/reprise, OAuth, révocation et restauration.
5. Ouvrir la bêta invitée uniquement après ces preuves. Ni facturation ni features entreprise supplémentaires ne sont nécessaires à ce lot.

## Correctifs de sécurité — 21 septembre 2026

Les constats ci-dessus décrivent l'état avant correction ; leurs numéros de
ligne sont historiques. R1–R7 sont traités dans le code : authentification des
contenus générés, échappement HTML OAuth, réservation des secrets OAuth,
confinement des accès fichiers avec os.Root et migration de la clé hors
workspace, validation Compose fermée, capacités de groupe limitées et OAuth
rattaché à son initiateur. R10 est traité par .dockerignore et une étape CI
vet/tests/race avant publication des images.

Compléments : contrôle Origin HTTP/WebSocket, cookies Secure sous HTTPS,
limites de requêtes et de tentatives de connexion, délais HTTP, attribution
atomique du premier administrateur. Les outils et leurs paramètres ne changent
pas ; les tentatives non autorisées sont refusées dans Prism.

Des tests de régression couvrent les liens symboliques, la migration de clé,
les secrets réservés, Compose, les routes privées et les capacités. Les tests
avec PostgreSQL jetable vérifient aussi le parcours OAuth complet, les secrets
de groupe et les inscriptions concurrentes. Voir docs/UPGRADING.md pour la
persistance de clé et les restrictions de compatibilité.

R8 (qualification des erreurs dans Activity) et R9 (concurrence des crons)
restent du travail fonctionnel séparé. Ceci ne certifie pas une isolation
Cloud : le Docker socket, les volumes partagés du mode entreprise, les widgets
de même origine et la coordination distribuée exigent toujours les frontières
d'exécution prévues pour le Cloud.
